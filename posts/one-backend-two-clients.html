One backend, two clients: how Silistudio is wired

  • Silistudio
  • Architecture
  • Java

Silistudio is an AI creative studio. You describe an image or a video, it generates it, and you edit and keep the result. It ships as an iOS app and a web app. Both talk to the same backend, and that single decision shapes almost everything else.

Why one API

Two clients with two backends means every feature gets built twice and drifts apart. With one API, the iOS app in SwiftUI and the web app in React are both thin: they render state and send intent. Billing rules, credit checks and generation logic live in one place.

Why reactive Java

The backend is Spring WebFlux with R2DBC on Supabase Postgres. Generation requests spend most of their life waiting on an inference provider. A blocking server would hold a thread for each of those waits. WebFlux holds none, so the server stays responsive while dozens of generations are in flight.

public Flux<GenerationEvent> generate(Prompt prompt, User user) {
    return credits.reserve(user, prompt.cost())
        .thenMany(inference.stream(prompt))
        .doOnError(e -> credits.release(user, prompt.cost()));
}

The snippet above is simplified, but it shows the shape: reserve credits, stream the work, and give the credits back if anything fails.

Where WebSockets earn their place

Image and video generation takes seconds to minutes. Polling for status wastes requests and feels slow. Instead, results stream back to both apps over a WebSocket, so progress shows up the moment it exists.

Payments

Stripe Checkout handles payment and webhooks confirm it. The lesson I keep relearning: the webhook route needs the raw request body to verify Stripe's signature, so it has to run before any middleware that parses JSON.

What is next

I am weighing a character builder that hands users exact prompts, so they waste fewer credits on misses. The open question is whether it earns its place or just adds weight. I will write that up when I decide.
