From push to production: Silistudio's CI/CD pipeline

  • DevOps
  • CI/CD
  • Silistudio

Writing the feature is half the job. The other half is getting it to users without breaking what already works. On Silistudio I own both halves, and the pipeline is what lets one person ship several times a day without holding their breath.

The pipeline at a glance

  1. Push. Every push and every pull request starts a GitHub Actions run.
  2. Test. The web app's Vitest suite runs, and the API image has to build cleanly.
  3. Build. Vite bundles the web app into ./dist; the API is packaged as a Docker image.
  4. Deploy. Only on main, and only if every job passed: the API goes out as a Docker web service on Render, the web app as a Render static site.

Pull requests stop after step three. That is the point: a branch can be as broken as it likes, but nothing reaches production until it is green.

The workflow

A trimmed version of the workflow file. Folder names are simplified.

name: ci-cd
on:
  push: { branches: [main] }
  pull_request:

jobs:
  web:
    runs-on: ubuntu-latest
    defaults: { run: { working-directory: web } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm, cache-dependency-path: web/package-lock.json }
      - run: npm ci
      - run: npx vitest run
      - run: npm run build          # Vite → ./dist

  api:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t silistudio-api ./api

  deploy:
    needs: [web, api]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: curl -fsS -X POST "${{ secrets.RENDER_API_DEPLOY_HOOK }}"
      - run: curl -fsS -X POST "${{ secrets.RENDER_WEB_DEPLOY_HOOK }}"

The deploy hooks are secrets, so the URLs that trigger a production deploy never appear in the repository. And because deploy needs both other jobs, one failing test is enough to stop the release.

What real deploys taught me

A broken build is CI working, not failing

One refactor left an import pointing at src/src/. Locally it was masked by a cached file; in CI, on a clean machine, the build failed immediately. Annoying for five minutes, but it meant users never saw it. A clean environment on every run is the most valuable thing CI gives you.

Single-page apps need a rewrite, not a redirect

The first deploy of the web app worked until someone refreshed a page like /projects and got a blank screen. The static host was looking for a file that does not exist. The fix is a rule that serves /index.html for every path, and it has to be a rewrite. A redirect changes the URL and the app loses its route.

Know where your build actually lands

Vite writes to ./dist. Older React setups wrote to ./build, and a lot of hosting docs still assume that. Pointing the host at the wrong folder deploys nothing at all, very successfully.

Middleware order is configuration, not style

Two production bugs came down to order. Cross-origin rules have to run before the routes they protect. And Stripe's webhook route needs the raw request body to verify its signature, so it has to be registered before anything parses JSON. Both pass every local test and only fail against the real services.

Long-lived connections need to survive deploys

Silistudio streams generation results over WebSockets. A deploy, or a service waking from idle, drops every open connection. The fix lives on both sides: a health check so the platform knows when the new instance is actually ready, and clients that reconnect quietly instead of showing an error.

What is next

  • Preview environments. A temporary deploy for every pull request, so changes can be clicked through before they merge.
  • A smoke test after deploy. Hit a few real endpoints once the release is live, and roll back automatically if they fail.
  • The iOS app in the same pipeline. Build and test on every push, with TestFlight uploads from main.
Full stack, to me, means the job isn't done when the code compiles. It's done when it's running for users, and you'd happily ship the next change tomorrow.
